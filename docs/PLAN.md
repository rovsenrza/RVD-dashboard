# План реализации «РВД Кабинет» — 40 рабочих дней

Статус выполнения ведётся в [docs/PLAN-STATUS.md](PLAN-STATUS.md). Этот файл — эталон объёма и порядка работ; при изменении объёма правим здесь и фиксируем причину в STATUS.

## 0. Исходная точка (день 0)

**Есть:**

- Frontend-скелет: React 19 / Vite / Tailwind v4 / TanStack Query+Table / Recharts, компонентная архитектура (`shared/ui` → `entities` → `features` → `app`), MSW-моки, CI (lint, arch-guard, typecheck, test, build).
- Домен из ТЗ (`entities/types.ts`), анализ референса ESM ([competitor-esm-analysis.md](competitor-esm-analysis.md)).
- Ответы 1С-разработчика: платформа 8.5, самописная конфигурация на БСП, OData пока не опубликован (опубликует нужное), тестовая база только локально, интеграция двусторонняя (заявки → 1С), история жизненного цикла есть, замены — сырые, моточасы будут в 1С.

**Нет:** backend, auth, реальных данных, сервера, дизайн-системы, экспорта, уведомлений.

**Доступ к 1С OData — день 1.**

## 1. Целевая архитектура

```
Browser (SPA)  ──HTTPS──►  BFF / API (Node + TypeScript)  ──OData/HTTP──►  1С (источник истины)
                              │
                              ├─ Postgres: кэш сущностей 1С + локальные данные
                              │  (пользователи, роли, уведомления, комментарии, фото, аудит)
                              ├─ Sync worker: инкрементальный опрос 1С (5 мин), upsert в кэш
                              └─ Outbox: заявки/замены → 1С с ретраями и статусом доставки
```

**Почему BFF, а не прямой OData из браузера:** креды 1С нельзя отдавать в SPA; OData 1С не умеет агрегаций для KPI; CORS; нужен свой слой для auth, ролей, multi-tenant и локальных сущностей, которых в 1С нет.

**Принцип разделения владения данными:**

| Данные                                                               | Владелец                  | Направление                      |
| -------------------------------------------------------------------- | ------------------------- | -------------------------------- |
| Рукав в сборе, Изделие, Контрагент, Филиал, Каталог, OEM, история ЖЦ | 1С                        | 1С → кэш (read-only)             |
| Заявки на замену/изготовление                                        | 1С (создаётся из ЛК)      | ЛК → 1С (outbox), статус 1С → ЛК |
| Факт замены, моточасы, введённые механиком                           | 1С (по ответу заказчика)  | ЛК → 1С (outbox)                 |
| Пользователи ЛК, роли, привязка к контрагенту/филиалу                | ЛК                        | локально                         |
| Уведомления, их настройки, прочитанность                             | ЛК                        | локально                         |
| Комментарии, фото, вложения на изделии                               | ЛК (уточнить: БСП-файлы?) | локально                         |
| Журнал действий пользователей ЛК                                     | ЛК                        | локально                         |

**Backend-стек (решение фиксируется в день 2):** Node 22 + Fastify + Prisma + Postgres + BullMQ/Redis для sync/outbox. Один язык с фронтом, общие типы через пакет `packages/contracts`. Альтернатива — NestJS, если команда предпочитает; на план не влияет.

**Монорепо:** `apps/web` (текущий фронт), `apps/api`, `packages/contracts` (Zod-схемы + типы, из них — и клиент, и валидация API).

### Неделя 4 (Д16–Д20) — Двусторонняя интеграция

**Д16 — Журнал замен (ТЗ 3.5)**

**Д17 — Outbox → 1С**

- Таблица `outbox` (тип, payload, статус: pending/sent/confirmed/failed, попытки, ответ 1С).
- Worker: POST в объект/HTTP-сервис 1С (по Д2), экспоненциальные ретраи, алерт при failed.
- Замена из Д16 уходит в 1С; статус доставки виден в UI.

**Д18 — Заявки и заказы (ТЗ 3.7)**

- Форма заявки из карточки изделия и из раздела: тип (замена/изготовление), изделие → автоподстановка характеристик, количество, комментарий, фото.
- `POST /requests` → outbox → 1С; `GET /requests` со статусами; sync статусов заявок из 1С (или webhook, если 1С сможет вызывать нас).

**Д19 — Уведомления (ТЗ 3.6)**

- Правила: окончание гарантии, плановая замена, превышение срока, осмотр; интервалы 30/14/7 (настраиваемые на контрагента).

**Д20 — Веха 4: полный цикл**

- Демо: изделие → приближение замены → уведомление → заявка → в 1С → статус вернулся → замена зафиксирована → история.

### Неделя 6 (Д26–Д30) — Качество и устойчивость

**Д26 — Sync: инкрементальность и отказоустойчивость**

- Инкрементальный опрос по дате изменения (если 1С отдаёт) или по версии; полная пересборка по расписанию (ночью). Индикатор «данные на HH:MM» в шапке; кнопка «Обновить сейчас» для admin.
- Поведение при недоступности 1С: кэш + баннер; outbox копит.

**Д27 — Производительность**

- Индексы Postgres под фильтры/сортировки; `EXPLAIN` на ключевых запросах; дашборд < 300 мс на 200 k изделий; виртуализация длинных списков на фронте; code-splitting по роутам.

**Д28 — Тесты**

- API: интеграционные тесты на каждый эндпоинт (auth, scope, пагинация, валидация). Adapters: 100 % на сэмплах 1С. Фронт: компонентные тесты примитивов + e2e (Playwright) на 5 ключевых сценариев: вход, поиск изделия, карточка, заявка, экспорт.

**Д29 — Безопасность**

- Rate limiting, helmet-заголовки, CSRF для cookie, валидация всех входов (Zod), секреты только в env, аудит зависимостей, скан OWASP ZAP baseline. Резервное копирование Postgres (pg_dump по cron + проверка восстановления).

**Д30 — Веха 5: release candidate**

- Все пункты ТЗ 3–6 закрыты или явно перенесены с согласием заказчика. CHANGELOG, версия 1.0.0-rc1.

## 3. Definition of Done (для каждой фичи)

1. Контракт в `packages/contracts` (Zod) + типы.
2. API-эндпоинт с проверкой scope/роли и тестами.
3. UI только из `shared/ui`-примитивов (arch-guard зелёный), loading/empty/error-состояния, мобильный вид.
4. Данные из 1С через адаптер с unit-тестом на сэмпле.
5. CI зелёный, задеплоено на stage, пункт отмечен в PLAN-STATUS.

## 4. Риски и меры

| Риск                                          | Вероятность | Мера                                                                                                    |
| --------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------- |
| OData публикуют частично / с задержкой        | высокая     | Д1: список нужных объектов заказчику; работаем на моках по mapping, адаптеры — на сэмплах; буфер Д36–38 |
