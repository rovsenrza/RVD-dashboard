## PURPOSE

«РВД Кабинет» — client cabinet for a hydraulic-hose (РВД) supplier's customers: every serialised hose → machine (гаражный номер) → installation place → lifecycle status → planned replacement → request. 1С (platform 8.5, custom БСП config, OData) is the source of truth; the cabinet is the lens plus the actions the customer owns (requests, where a hose sits, comments, files); installation dates and replacements are the supplier's (1С). Russian-only UI. Reference: Eurohydroservice ESM. Plan: docs/PLAN.md, docs/PLAN-STATUS.md; product: PRODUCT.md; design: DESIGN.md.

## STACK

npm workspaces: `packages/contracts` (@rvd/contracts — domain types and the status rule, shared by web and API), `apps/api` (@rvd/api — Fastify BFF: Postgres cache via `pg` and SQL migrations (no Prisma: nothing to generate in CI or on Vercel), full sync from 1С, `GET /products` filtered/searched/sorted/paged in SQL with the status rule mirrored in SQL (tested against the TypeScript rule); every page carries both registry tabs' counts under the same filters (`ProductPage.counts`, counted apart from the page), and the search text holds the hose's numbers, name, machine garage number and place, health, env config, read-only 1С OData client with retries, pure adapters 1С → contracts with tests, `npm run onec:smoke -w @rvd/api` reads the live base, `npm run perf -w @rvd/api` times the key requests on 200 000 synthetic hoses in a schema of its own (Д27: every client-scoped request under 25 ms, the all-clients dashboard 82 ms)); the web app stays at the repo root for now because Vercel builds from it, and moves to apps/web later. Hybrid mode: `VITE_LIVE_API=true` (old name `VITE_LIVE_PRODUCTS`) lets the mocks pass through exactly the routes apps/api serves — the list `LIVE_ROUTES` in src/shared/api/live.ts: products, hose history and lifetime, equipment and its hoses, dashboard summary, requests, sign-in and `/me` — and the Vite dev server proxies `/api` to apps/api (port 3001). Sign-in (Д6–Д7): companies (`companies.onec_client_key` = the 1С Клиент_Key) and users (scrypt hashes) live in Postgres (migration 005); `POST /auth/login` answers a 15-minute HS256 access token (node:crypto, no library) and sets the 30-day refresh token as the httpOnly cookie `rvd_refresh`, stored hashed in `sessions` and rotated on every `POST /auth/refresh`; `POST /auth/logout` revokes it; a refresh token is claimed under a row lock and names its successor (migration 006), so of two requests with one token (two tabs restoring at once, a reload during a renewal) one rotates it and the other gets an access token without a new cookie for 30 s while the successor lives; `GET /me` says who and which company. Every route but `/health` and `/auth/*` needs `Authorization: Bearer`, and every query is scoped to the token's company client (`clientOf` in app.ts), so a company sees only its own 1С client's hoses, machines, dashboard and requests. apps/api refuses to start without `JWT_SECRET` (32+ characters) unless `AUTH_DISABLED=true`, which wins over a secret: then everyone is the demo user, scoped to `CABINET_CLIENT_KEY` when set; `COOKIE_SECURE=true` behind HTTPS; the company's administrator manages its users (`/admin/users` GET/POST/PATCH, `/admin/users/:id/reset-password`: admin only, own company only, nobody changes their own role or access, switching access off ends the user's sessions); without a mail server (customer question 7) a new or reset password is a one-time password returned once (`PasswordDelivery` kind `password`; the demo answers kind `email`) and the person must replace it (`users.must_change_password`, migration 007, claim `mcp`): until then the server answers only `/auth/password` and `/me` and the web app shows «Новый пароль» instead of the cabinet; `POST /auth/password` (current + next, the shared `passwordProblem` rule: 10+ characters) ends every other session and returns fresh tokens. The first administrator of a company comes from `npm run user:add -w @rvd/api`. A live cabinet's «Администрирование» shows only «Пользователи» — branches, settings, import and the journal still run on the demo's data. The web app keeps the access token in memory only (src/shared/api/client.ts: one refresh at a time for the whole page — restoring on load and renewing on a 401 share it — then sign-out). The registry «Мои изделия» pages, sorts and searches on the server (`useProductPage`, DataTable `server` mode, «Экспорт» fetches every matching row); the mock answers the same query the same way (src/shared/mocks/productList.ts), and no screen holds the whole registry: lookups ask the server — ⌘K and the hose picker (request form, contact dialog) through `useProductSearch` as the person types (a picker shows the preset machine's hoses before that), the scanner and a number typed and left through `useFindProducts`, the exact match staying on the client (`matchCode`, `findProduct`); only «Экспорт» and the admin import take a whole query (the API's largest page, 5 000). Live data is not narrowed by branch yet: one company is one 1С client, and branch-bound users come with the users screen on the API. Requests (Д17–Д18): `POST /requests` checks the request with `requestProblem` against the cache (only the cabinet client's own hoses), rebuilds hose lines from the hose and stores it in the cabinet's own `requests` table (never touched by a sync); the outbox sends due requests to 1С's order service (`ONEC_ORDERS_URL`, docs/1c/request-api.md) with the request id as `Idempotency-Key`, keeps the СВЦБ number on success, the reason on a refusal (422) and retries with growing pauses when 1С is down; the sync reads order statuses back from OData. `ServiceRequest.delivery` (queued / delivered / refused) and `deliveryNote` tell the client where a request stands; until the real service exists `npm run fake-1c -w @rvd/api` answers like it. ## PATTERNS

- Two status axes (Д2): `ProductStatus` — health, the primary UI axis, derived only by `packages/contracts/src/status.ts` (Д13; the web imports it through `entities/product/rules.ts`): start = installedAt, else shippedAt; «Внимание» = last `warnDays` before the planned date or last `warnPercent` % of life (`warnRule`, admin setting; the customer settled on the last 30 days, the default); the boundary day belongs to the later phase; statusOf/serviceDates/lifetimePhases/daysLeft serve mocks, BFF and UI alike; `ProductLifecycle` — the 1С workflow (Изготавливается → … → Списан), from the statuses register `InformationRegister_СтатусыИзделий` and never from the documents (the 1С developer's rule, 2026-10-03: «Выпуск» changed shape over the years and «Заказ» set statuses too); the machine is the garage number on the «Выпуск» that recorded the status. Status text uses the -ink tier (AA). Notifications (Д19) come from a daily server job over the same phases and the company lead days; read state and per-user prefs live on the server.
- The two-level model is Каталожный номер → Изделие, not the ESM naming: `CatalogNumber` is the reference типоразмер (life, warranty, diameter, braid count, default composition) and `Product` copies those plus its own `composition` (hose + couplings + fittings from `ComponentItem`). Заявка maps to the 1С «Заказ клиента» (СВЦБ-number, branch, positions, shipment status), which syncs to a separate 1С:УТ base — see docs/1c/entities.md.
- Adding a feature: type in entities → hook in shared/api/queries → MSW handler + generator → page from shared/ui primitives → lint:arch green.
- UI work: impeccable skill + `impeccable context`, follow DESIGN.md; no bordered cards; detector clean; finish review before a redesign ships.
- Empty values via EmptyValue; shaped skeletons; ErrorState with retry. Mocks read the demo role from `rvd.role` (the BFF: from the token).
- Files (Д25): `Attachment.url`/`previewUrl` come from the server (BFF route or signed link). Forms upload each file as a draft on pick and submit the ids; the server binds them. Limits in `entities/attachment`, checked by form and server; antivirus: EICAR on mocks, ClamAV on the BFF. Downloads via fetch → Blob (carries the session). Stored in the cabinet, not 1С БСП (PLAN.md §5 q5).
- Reports (Д21): the server builds a `Report` (typed columns, all rows in scope, totals); the browser writes Excel from it and prints /reports/print (A4 landscape, always light) for PDF; the BFF will serve .xlsx/.pdf for the same query. Registry «Экспорт» = what the table shows. Excel dates are UTC midnights.
- Installation dates belong to the supplier (customer, 2026-10-03): 1С sets them, the cabinet shows `installedAt ?? shippedAt` and never writes the field — not from the card, not from the Excel import. A wrong date goes to the specialist through «Связаться со специалистом» (`support.message` in the action log).
- Requests (customer, 2026-10-03): `RequestKind` = replace | manufacture | repair, checked by one rule, `requestProblem` in packages/contracts/src/requests.ts (the mock now, the BFF later). «Замена» lines name the company's own hoses (`RequestPosition.productId`; made, archive included) and the server rebuilds number and machine from the hose; «Изготовление» and «Ремонт» take catalogue numbers (an unknown one goes as text for the manager) or no lines when an Excel file is attached; at most `MAX_REQUEST_POSITIONS` = 10. 1С's «Заказ клиента» has no type field yet (open question for the 1С developer). A replacement is asked for, never recorded here: «Заявка на замену» on the hose card (the hose chosen), the machine card (its hoses first) and the journal; 1С writes the old hose off and links the new one (`ЗаменяемоеИзделие_Key` → `replacedProductId`).
- Every mutation writes an action-log line (who, when, object, fields before → after) as display strings; unchanged saves write nothing. Mocks record it in handlers; the BFF in middleware (Д23).

## TRADEOFFS

- Mocks first, integration later: UI is stable against 1С schema churn because adapters map 1С → entities/types.ts; cost is a second data model to maintain.
- Client-side pagination now; server-side mandatory from Д5 (reference has 170k hoses).
- Dark theme via role tokens: light values in @theme, dark set redefined for prefers-color-scheme and data-theme (rvd.theme, applied pre-paint); tokens.test.ts guards parity and AA. Sign-in is real in live mode; the demo keeps a mocked session that accepts any address.
- impeccable skill vendored in .claude/skills without its 12 MB binary (re-run `npx impeccable install`).
- Customer docs, video frames, .env*, review screenshots are gitignored.
- The ADR lives in the codebase-memory DB and is wiped on tool updates; docs/ADR.md is the committed copy — restore with `codebase-memory-mcp cli manage_adr --args-file` when `manage_adr get` returns no_adr.

## PHILOSOPHY
