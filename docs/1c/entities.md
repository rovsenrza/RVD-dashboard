# 1С: структура (черновик по демонстрации разработчика, Д1)

Источник: скрин-шеринг (AnyDesk) с разработчиком заказчика, 2026-09-17. Разработчик показал прикладной веб-клиент («РВД», тонкий клиент, `sk.neo-link.ru/rvd/...`), не Конфигуратор и не `$metadata` напрямую — поэтому ниже приведены **разделы/реквизиты интерфейса**, а не подтверждённые технические имена OData entity sets. Точные имена (`Catalog_...`, `Document_...`) нужно получить отдельно — либо экспортом `$metadata`, либо попросив разработчика показать список опубликованных веб-сервисов.

## Разделы меню

Настройки (Филиалы и пользователи, Клиенты) · Парк техники · Изделия · Документы выпуска · Заявки · Каталог и комплектующие

## Сущности

### Парк техники (→ наш `Equipment`)

Код, Клиент, Тип, Марка, Модель, Гаражный номер, Инвентарный номер. Вкладки карточки: Основное, Изделия (список установленных РВД). Изделие может быть «без привязки к технике».

### Изделия (→ наш `Product`, двухуровневая модель Рукав в сборе → Изделие)

УникальныйНомер, Клиент, Техника, Код, Изделие (наименование), Статус, Статус гарантии, Номер OEM, Заменяемое изделие, Номенклатурный номер, Срок полезного использования (дни, напр. 365), Срок гарантии (дни, напр. 180), Диаметр, Количество оплеток/навивок, Состав (табличная часть: Комплектующие/Количество — BOM рукав + муфты + фитинги).

Статусы, встреченные в интерфейсе: **Изготавливается → На складе → Отгружен**; также отдельно встречается статус/сущность **«Рукав в сборе»**. Кнопки жизненного цикла: Оформить, Выпустить, Передать в эксплуатацию, Заменить, Списать.

Виджет остатка ресурса — шкала-спидометр 0–180 с зонами зелёная/жёлтая/красная («Новый → … → Требуется замена») — подтверждает нашу модель «статус считается от installedAt + serviceLifeDays».

### Каталожные номера (→ справочник эталонных типоразмеров)

Код, Наименование (артикул, напр. «02753-00613»), Срок полезного использования, Срок гарантии, Диаметр, Количество оплеток/навивок, состав по умолчанию. Выбор каталожного номера в карточке Изделия автоподставляет наименование и состав.

### Каталог и комплектующие (→ справочник компонентов)

Наименование, Код, Показатель, Производитель, **Тип**: Защита / Муфты / Прочее / Рукава / Сростки / Фитинги.

### Документы выпуска (→ история ЖЦ / журнал событий)

Документ, Автор, Статус, Изделие, Тип документа (всегда «Выпуск»), Дата, Номер, Клиент. Каждая смена статуса Изделия фиксируется отдельным документом; документ связан с Заказом клиента как основанием.

### Заявки = «Заказы клиента» (→ наш `Request`)

Список: Дата, Номер (формат «СВЦБ-XXXXX»), Дата загрузки, Статус обмена заказа, **Детальный статус в УТ** (обмен с отдельной базой 1С:УТ — важно для Д2/Д17, outbox), Статус (Выполнен/К выполнению), Отгрузка, Клиент, Филиал, Комментарий, Автор.
Карточка: + Статус заказа, Статус отгрузки. Кнопки: Провести и закрыть, Создать на основании, Выгрузить заказ, Выгрузить сборку, Добавить изделия, Изготовлен, Отгрузить.
Табличная часть: Техника, Каталожный номер, Изделие, Номенклатурный номер, Статус изделия, Статус отгрузки, Индивидуальный номер, Комментарий.

### Клиент / Филиал (→ наш Contragent/Branch)

Примеры филиалов одного клиента: Новокузнецк, ОП Эльга, ОП Восточное, Удоканская Медь, Магадан. Клиент может иметь суффиксы подразделений («КСТ УАТ», «УРГО»).

## Открытое (нужно уточнить у разработчика отдельно)

- Точные имена OData entity sets для всех перечисленных объектов
- Является ли «Заявка» в нашем ЛК тем же документом «Заказ клиента», или нужен отдельный лёгкий документ на стороне 1С
- Обмен с 1С:УТ — влияет ли на то, как/куда наш BFF должен писать (напрямую в РВД-базу или через УТ)
- Реквизит фильтрации клиента/филиала для OData-запросов (кандидат: поле «Клиент» + «Филиал», подтверждено что фильтруется в разделе Заявки)

## Аудио-заметки с созвона (ses2, 2026-09-17)

Разработчик предложил два варианта интеграции:

1. **Сырые данные через OData**: мы читаем напрямую регистры/справочники (сырые данные), сами компонуем на своей стороне.
2. **Готовые API-функции**: он пишет под наш запрос конкретные функции/HTTP-сервисы, которые сразу возвращают скомпонованный результат (но это дольше — «функций готовых нет», разрабатываются под заказ).
   Его позиция: вся бизнес-логика и обработка — **на нашей стороне**, он лишь даёт доступ к данным (сначала расшарил доступ на чтение к «филиалам» и части объектов, свои специфичные объекты пока не включил в стандартную подсистему OData — надо будет запросить отдельно). Договорились: на первом этапе (Д1–Д5) мы готовим каркас с нерабочими закладками/демо-данными, интеграция — когда решим, каким из двух путей идти.
