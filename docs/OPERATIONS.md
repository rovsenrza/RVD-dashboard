# РВД Кабинет — эксплуатация

Для того, кто ставит кабинет на сервер и следит за ним. Как устроен код — в [ADR.md](ADR.md); что сделано и что ждёт ответов — в [PLAN-STATUS.md](PLAN-STATUS.md).

## Из чего состоит

| Часть    | Что делает                                                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `web`    | nginx: отдаёт приложение, `/api` передаёт в API, ставит заголовки безопасности (CSP и др.)                                                          |
| `api`    | Node 22: вход, данные компании, заявки в 1С, синхронизация с 1С (проверка каждые 10 минут, полная — ночью), почта, файлы. Миграции — сам при старте |
| `db`     | Postgres 17: кэш 1С и всё, что есть только у кабинета (пользователи, заявки, журнал, настройки, места установки, комментарии, обращения, файлы)     |
| `clamav` | Антивирус для загружаемых файлов. Нужно около 1,5 ГБ памяти; без него ловится только тестовый файл EICAR, о чём API пишет при старте                |

Шаблоны — в `deploy/`: `api.Dockerfile`, `web.Dockerfile`, `nginx.conf`, `docker-compose.prod.yml`. Сборка проверена локально целиком: вход через nginx, реестр, загрузка фото с миниатюрой, подписанные ссылки на файлы, отчёты.

## Первый запуск

1. Docker и Docker Compose на сервере; доступ сервера к OData 1С (отдельный пользователь 1С только на чтение; при необходимости IP в белом списке 1С).
2. `cp .env.example .env` и заполнить:
   - `ODATA_URL`, `ODATA_USER`, `ODATA_PASSWORD` — продуктивная база 1С;
   - `JWT_SECRET` — 32+ случайных символа: `openssl rand -base64 48`;
   - `DB_PASSWORD` — пароль Postgres;
   - `CABINET_URL` — адрес кабинета (например `https://rvd.example.ru`);
   - когда будут: `ONEC_ORDERS_URL` и его пользователь (сервис заявок 1С), `SMTP_URL`, `MAIL_FROM`, `SUPPORT_EMAIL`.
3. `docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d --build`
4. Первая синхронизация с 1С начинается сама; ход — `docker compose -f deploy/docker-compose.prod.yml logs -f api` (строка «синхронизация с 1С»).
5. Первый администратор компании-клиента (дальше пользователей своей компании он ведёт сам на экране «Пользователи»):
   ```sh
   docker compose -f deploy/docker-compose.prod.yml exec api npx tsx src/auth/cli.ts \
     --company "ООО …" --client <Клиент_Key из 1С> --name "Фамилия Имя" \
     --email … --password … --role admin
   ```
   `Клиент_Key` — ссылка клиента в 1С (`Catalog_Клиенты`). Выданный пароль человек сменит при первом входе.

## HTTPS

Кабинет нужно открывать только по HTTPS: refresh-cookie помечен `Secure` (`COOKIE_SECURE=true` по умолчанию в compose), по HTTP вход не переживёт перезагрузку страницы. TLS завершается либо на прокси хоста (nginx/Caddy/балансировщик заказчика — тогда пробросить его на порт `HTTP_PORT`), либо в `deploy/nginx.conf` (добавить `listen 443 ssl` и сертификаты). Решается вместе с сервером и доменом (вопрос 8).

## Обновление

```sh
git pull
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d --build
```

Миграции применяются при старте API. Перед обновлением — бэкап.

## Бэкапы

`scripts/backup.sh` сохраняет всё, что есть только у кабинета, и файлы; строки кэша 1С не сохраняются — синхронизация восстановит их за секунды. Хранятся 14 последних (`BACKUP_KEEP`). Ночью по cron:

```sh
0 2 * * * cd /opt/rvd && PG_DUMP="docker compose -f deploy/docker-compose.prod.yml exec -T db pg_dump" \
  FILES_CMD="docker compose -f deploy/docker-compose.prod.yml exec -T api tar -czf - -C /data/files ." \
  scripts/backup.sh >> backups/backup.log 2>&1
```

Папку `backups/` стоит копировать за пределы сервера.

Восстановление (API остановить):

```sh
docker compose -f deploy/docker-compose.prod.yml stop api
PG_RESTORE="docker compose -f deploy/docker-compose.prod.yml exec -T db pg_restore" \
  RESTORE_FILES_CMD="docker compose -f deploy/docker-compose.prod.yml exec -T api tar -xzf - -C /data/files" \
  scripts/restore.sh backups/db-….dump backups/files-….tar.gz
docker compose -f deploy/docker-compose.prod.yml start api
```

Кэш 1С заполнится первой же синхронизацией после старта. Восстановление проверено на копии базы.

## Наблюдение

- `GET /api/health`: `200` и `status: "ok"`; `"degraded"` — 1С не отвечает (кабинет работает на кэше, поле `onecUnavailableSince`); `503` — нет базы. Подходит для внешнего мониторинга; в контейнере API тот же адрес — его healthcheck.
- Логи — `docker compose … logs api` (JSON). Важные строки: «синхронизация с 1С», «1С недоступна, данные — из кэша», «почта не отправлена», «ClamAV не задан».
- Пользователи видят свежесть данных внизу боковой панели («Данные 1С на 14:32»), а если 1С молчит дольше 30 минут — баннер под шапкой. Администратор компании может запустить проверку 1С сразу.

## Синхронизация с 1С

Проверка каждые 10 минут (`SYNC_INTERVAL_MS`) берёт из 1С только изменившиеся изделия; полная пересборка — в 3:00 (`SYNC_FULL_HOUR`) или если ночь пропущена. Вручную: `docker compose … exec api npx tsx src/sync/cli.ts` (полная) или с `--check`. Если API запущен в нескольких экземплярах, синхронизацию оставить в одном (`SYNC_ENABLED=false` в остальных) — ограничение попыток входа тоже живёт в памяти одного процесса.

## Почта

Включается заданием `SMTP_URL` (вопрос 7): ежедневная сводка уведомлений с `NOTIFY_HOUR` (по умолчанию 7:00) тем, кто включил письма, если компания разрешила письма в настройках; обращения «Связаться со специалистом» — на `SUPPORT_EMAIL` (вопрос 15), неотправленное повторяется. Без SMTP ничего не отправляется и не помечается отправленным.

## Файлы

Хранятся в томе `rvd-files` (`FILES_DIR=/data/files`), до 10 МБ, JPG/PNG/WebP/PDF/Word/Excel; сервер проверяет формат, начало файла и антивирусом. Ссылки на файлы подписаны и действуют до двух часов. Черновики формы заявки, которые не прикрепили, удаляются через сутки. Перенос в S3 — когда будет понятен сервер (интерфейс хранилища это предусматривает).

## Что ждёт ответов

Сервис заявок 1С (без него заявки ждут в очереди, клиент видит «Отправляется в 1С»), SMTP и адрес для обращений, сервер и домен, деление крупного клиента на филиалы, перенос изделия на другую технику, публикация справочника моделей и документов в OData — подробно в PLAN-STATUS.md, «Открытые вопросы».
